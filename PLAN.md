ContractGuard Agent — Implementation Plan
Transform waku-agent into ContractGuard, a contract-review agent with semantic, episodic, and procedural memory, while preserving Waku's existing Harness / Loop / Memory / Eval architecture.

0. How to Use This Plan
This file is the implementation roadmap for the ContractGuard adaptation.

AGENTS.md remains the repository-wide engineering rulebook and takes precedence whenever this plan conflicts with repository constraints.

5. Memory Design
5.1 Semantic Memory
Purpose:

Store durable contract-domain knowledge.

Examples:

clause definitions;
common lexical variants;
known red flags;
standard review guidance;
safe fallback explanations;
reusable clause patterns.
Example conceptual record:

{
  "clause_type": "Uncapped Liability",
  "definition": "A liability provision that does not establish a maximum monetary exposure.",
  "risk_level": "HIGH",
  "red_flags": [
    "unlimited liability",
    "without limitation",
    "no cap"
  ],
  "review_guidance": [
    "Check for a liability cap",
    "Check exclusions for indirect damages",
    "Check insurance obligations"
  ]
}
Semantic memory must contain durable knowledge, not a raw copy of every reviewed contract.

5.2 Episodic Memory
Purpose:

Store prior contract-review events.

Minimum useful fields should include:

contract_id
contract_name
clause_type
risk_level
finding_summary
evidence
review_recommendation
timestamp
Example query:

What was the latest reviewed contract containing Uncapped Liability, and what conclusion was reached?

Episodic memory represents what happened in a previous review, not general legal knowledge.

5.3 Procedural Memory
Purpose:

Store how to review each clause type.

Create one clause-review skill / runbook per target clause.

Target directory:

skills/clauses/
Expected files:

termination_for_convenience.md
uncapped_liability.md
cap_on_liability.md
ip_ownership.md
non_compete.md
change_of_control.md
governing_law.md
indemnification.md
confidentiality.md
exclusivity.md
Example procedure:

Uncapped Liability

1. Locate liability / damages / indemnity language.
2. Search for cap / limit / maximum / aggregate liability language.
3. Determine whether liability exposure is bounded.
4. Check exclusions for consequential / indirect damages.
5. Check carve-outs from liability limitations.
6. Check insurance requirements.
7. Produce grounded evidence and a recommendation.
5.4 Retrieval Gate
The retrieval gate should answer:

Does this specific review step need long-term memory?

Examples:

Memory retrieval is useful when:

a clause is ambiguous;
the review can benefit from historical examples;
the same clause type has appeared previously;
semantic guidance is needed;
risk interpretation is non-trivial.
Memory retrieval may be skipped when:

deterministic parsing is sufficient;
metadata can be directly extracted;
current context already contains everything needed.
The purpose is to avoid unnecessary context injection and token use.

5.5 Consolidation
After a completed review, consolidation may extract reusable knowledge such as:

previously unseen clause wording;
reusable red-flag patterns;
review heuristics;
recurring risk structures.
Do not blindly convert every review output into semantic memory.

A new semantic-memory item should be:

durable;
reusable across contracts;
grounded in reviewed evidence;
meaningfully different from existing knowledge.
6. Evaluation Principles
6.1 Primary Deterministic Evaluation
CUAD should primarily evaluate clause extraction.

Metrics:

Precision
Recall
F1
per-clause metrics
macro average
micro average
The evaluator must define:

text normalization;
span normalization;
duplicate handling;
overlap criteria;
matching threshold.
The same evaluator must be used for every ablation arm.

6.2 Important CUAD Limitation
CUAD provides clause-category and span annotations.

It does not directly provide gold labels for:

HIGH
MEDIUM
LOW
Therefore:

Do not interpret:

clause exists == HIGH risk
as ground truth.

Risk-scoring quality must be evaluated separately.

6.3 Risk Scoring Evaluation
Possible evaluation methods:

Deterministic rule consistency
For carefully designed synthetic / curated cases:

expected HIGH
expected MEDIUM
expected LOW
Use explicit rules where the expected label is deterministic.

LLM-as-Judge
Secondary evaluation dimensions:

evidence correctness;
reasoning quality;
recommendation usefulness;
groundedness;
readability.
LLM-as-Judge is supporting evidence, not a replacement for CUAD deterministic extraction metrics.

6.4 Memory Ablation
Core experiment:

baseline
semantic_only
full_memory
baseline
no persistent semantic review memory;
no prior review episodes;
review each contract independently.
semantic_only
seeded clause-domain knowledge available;
no accumulating review history.
full_memory
semantic memory enabled;
episodic review history enabled;
procedural runbooks enabled;
relevant memory accumulates across contracts.
All arms must use the same:

model;
target clause list;
prompt version;
dataset split;
contract order;
temperature / decoding settings;
evaluator;
parsing rules.
Each arm must run in an isolated memory state.

Do not allow memory from one arm to leak into another.

6.5 Ablation Metrics
Record at least:

Precision
Recall
F1
critical clause miss rate
average review latency
LLM calls
input tokens
output tokens
retrieval count
memory items retrieved
When cost metadata is available, also record estimated or exact model cost.

Do not claim that full memory improves performance unless the measured results actually show an improvement.

If memory hurts performance, report it.

That result is still valuable engineering evidence.

Architecture decisions:

- Keep domain behavior opt-in and reuse the existing Memory facade, SQLite
  stores, provider client, skill loader, slot gate and observer events.
- Require local stores for this foundation; reject remote adapters before
  construction rather than promise untested remote enumeration or consistency.
- Use versioned JSON summaries instead of changing database or store interfaces.
  Exact history lookup scans decoded episodes beyond default top-k limits and
  compares timezone-aware timestamps.
- Skip contract memory when strict domain gate validation fails; preserve the
  personal-assistant gate's original fail-open behavior when review mode is off.
- Store history immediately on validated completion. Consolidate reusable cues
  separately from generic chat batching; review mode does not consolidate chat.
- Permit benchmark predictions as future historical episodes while preventing
  them from teaching semantic patterns. The caller owns origin provenance.
- Keep domain facts local. No new default dependency, core tool, graph engine,
  dashboard route or hosted/runtime code transfer is introduced.

Execution path for study:

`Memory` initialization -> ten idempotent clause facts in `facts`.
Gateway -> Session.build_system -> preserved SOUL.md plus review instructions
-> small-model review gate -> selected clause facts and decoded historical
reviews -> matching SKILL.md bodies -> existing agent loop and provider.
Phase 1 does not call a review toolchain. A caller supplies a completed finding
and its source to `Memory.complete_review()` -> exact evidence validation
-> versioned `episodes` summary -> optional small-model pattern proposals
-> grounding, provenance and novelty filters -> optional slot gate
-> reusable facts with `contractguard_consolidation` provenance.
Observers receive gate decisions, retrieval counts, model usage, episode events
and kept-fact records. SQLite retains ordinary chat history; procedures remain
files loaded into the system prompt.

Learning checkpoint:

- Gold contamination can make an agent repeat the reference answer instead of
  finding evidence. CUAD annotations belong to scoring; memory contains fixed
  domain facts and explicitly permitted prior predictions. Source quotations
  legitimately overlap gold text, but annotation objects and expected labels
  never enter context or memory writers.
- A shared home would let another arm's predictions or seeds change a later
  arm's task. Fresh homes, fixed procedures and disabled cache/semantic learning
  make baseline, semantic-only and full-memory policies identifiable.
- Micro F1 pools TP/FP/FN, so categories with many spans contribute more. Macro
  F1 averages the selected category F1 values, including zero-support categories,
  so a common Governing Law category cannot hide a rare category's failure.
- Exact matching rejects a larger correctly grounded quotation when its boundary
  differs. IoU can count that overlap as a match; a threshold change changes
  recall without changing predictions. The primary character-IoU threshold stays
  at 0.5 across arms. One-to-one maximum matching prevents duplicate credit.
- A judge can assess recommendation prose but adds model opinion and variability.
  It cannot replace deterministic source offsets or create CUAD risk gold. This
  phase chooses separate explicit authored risk rubrics instead of a judge.

  held-out sources, stable policies, error accounting and repeated measurements

  an increasing episode count establish no quality improvement.

9. Engineering Rules Specific to ContractGuard
9.1 Grounding
Every extracted positive clause finding must carry source evidence.

Never produce:

HIGH risk: Uncapped Liability
without identifying the source text that caused the finding.

9.2 Structured Intermediate Results
Prefer:

{
  "clause_type": "...",
  "found": true,
  "spans": [],
  "risk_level": "...",
  "reasoning": "...",
  "recommendation": "..."
}
over passing unconstrained prose between internal stages.

Reports are a presentation layer.

Evaluation must consume structured outputs.

9.3 No Benchmark Gaming
Never:

insert CUAD answers into the prompt;
use gold answers as memory;
tune thresholds independently for each ablation arm;
omit failed contracts from one arm but not others;
silently change model versions between comparisons;
report only favorable clause categories.
9.4 Deterministic Tests First
For any new behavior, first ask:

Can the contract of this behavior be tested without an LLM?

Examples:

parser offsets
schema validation
memory persistence
memory isolation
skill triggering
retrieval-gate routing
span scoring
report grounding
These should be deterministic.

Use LLM-dependent evaluations only where unavoidable.

9.5 Observability
Whenever possible, preserve / extend Waku's existing tracing rather than building custom logs.

Important events include:

memory items retrieved
clause extraction invoked
clause found / not found
risk scorer invoked
report generated

consolidation executed
Do not log secrets or full sensitive user data unless consistent with existing Waku local-first behavior and repository conventions.
